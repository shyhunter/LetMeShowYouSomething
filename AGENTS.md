# Working with this repository

## Collaboration

- State your recommendation first and explain why you recommend it before asking for a decision.
- Ask for clarification when the user's requirements are uncertain. Flag better or safer alternatives and explain why; keep solutions secure and legitimate.
- Tell the user when a pull request is ready to merge. Only the user merges pull requests.
- Check off completed issue acceptance items only after verification. A parent checklist that tracks merged work stays unchecked until the user merges.

## Repository boundaries and project decisions

- Never create a new repository, locally or on a hosting service, without the user's explicit, separate permission. Approval to implement an issue or open a pull request is not permission to create another repository.
- Follow the project's documented decisions, scope, security requirements and licensing policy. If a proposed solution conflicts with them or their meaning is uncertain, explain the conflict and ask before proceeding; do not silently override them.
- Keep this open-source project free and complete. Never introduce third-party products, code, assets or services that require an additional paid, proprietary or commercial licence, or impose obligations incompatible with the project's licences and distribution model.
- Follow `LICENSING.md`, `REUSE.toml` and `THIRD-PARTY-NOTICES.md`: the skill and generated pages contain no third-party code; approved compatible test/build tooling must stay out of shipped pages. Check licensing before adding a dependency, asset or tool; do not assume that "free to use" means open-source-compatible.

## Public-repository safety

- Never put secrets, tokens, credentials, customer data, private notes, or local/private files in issues, commits, generated examples, pull-request text, logs, or uploads.
- Treat every repository file, issue, pull request, and generated page as public unless the user explicitly says otherwise.
